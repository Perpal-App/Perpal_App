# Session-authoritative auth routing with protected tab fallback

The change moves auth navigation into a root gate backed by Privy readiness and user state. Initial restoration renders a neutral state instead of mounting onboarding, while later transient not-ready periods retain the last confirmed branch so OAuth handoff does not tear down `/access`. `Stack.Protected` partitions onboarding/auth from the authenticated tabs, making login, logout, expiry, deep links, and Back navigation converge on route-set replacement rather than imperative redirects. Once all new files are included, the traced transitions satisfy the stated navigation invariant.

**Watch for:** **High — confirmed:** the gate and authenticated route tree are untracked, so the tracked patch cannot build or ship this behavior. **Medium — confirmed:** `AuthNavigationGate` fails the repository lint rule at line 38. **Medium — confirmed:** no automated coverage exercises the auth-state and deep-link matrix, including passive expiry.

## High-level view

The gate mounts no navigator until Privy first reports a ready, error-free session, then gives the current authoritative state precedence over the retained state. A later `isReady=false` keeps the last confirmed branch rather than treating uncertainty as logout; an initialization error preempts both branches with a fail-closed error screen.

Expo Router 57 removes false-guard screens from the navigator’s route-name set, prunes invalid history entries, and creates the first still-allowed route when none survive. The declared order makes `(tabs)` the authenticated anchor and its `initialRouteName="home"` produces `/home`; the unauthenticated anchor is `index`.

Email and OAuth success now rely on one authority: Privy’s user publication flips the root route set. The `/access` callback remains available during an unresolved handoff and is removed once authentication is authoritative; the configured `perpal` scheme matches `redirectUri: '/access'`.

Successful logout and confirmed passive expiry remove tabs and return to onboarding, while a rejected logout leaves the authenticated tree mounted with an error. Route protection is UI containment, not API authorization; future protected operations still need fresh-token and server-side enforcement.

Safe-area ownership remains centralized in the seeded root provider and `AppScreen`. The remaining blockers are delivery completeness, one new lint failure, and the absence of regression tests for this state machine.

## Session resolution covers cold start, warm handoff, and initialization failure

Before Privy produces a ready, error-free result, `SessionResolutionState` renders through `AppScreen`; neither `index` nor `(auth)` mounts, so a restored user cannot see onboarding on the first frame. Ready-plus-user exposes only `(tabs)`, while ready-plus-null exposes only `index` and `(auth)`. This covers ordinary cold and warm starts without an auth UI flash.

After first resolution, `currentSession ?? lastResolvedSession` retains the prior branch only while the current state is non-authoritative. A transient `isReady=false` during OAuth therefore keeps `/access` mounted for an unauthenticated handoff and keeps tabs mounted for an authenticated session. A newly authoritative result wins immediately, so email login, OAuth completion, confirmed expiry, and logout do not wait for the retention effect before changing guards. No stale route reversal is evident in this precedence model; the effect is a lint and extra-render problem rather than a demonstrated navigation race.

An initialization error bypasses both the retained state and navigator. Restored users therefore fail closed on the session error screen rather than falling through to onboarding, and users are not classified as unauthenticated from a failed initialization.

## `Stack.Protected` prunes history and selects deterministic anchors

The installed Expo Router 57.0.9 implementation excludes false-guard names before building the navigator. Its stack router filters existing entries against the new route-name set and creates `routeNames[0]` if no route survives, confirming both the fallback and Back behavior.

For an authenticated session, `index` and `(auth)` are absent and `(tabs)` is the only root route; its tab initializer selects `home`. Authenticated deep links to `/` or `/access`, and login while on either auth route, therefore resolve to `/home` with no auth entry left in history. For an unauthenticated session, `(tabs)` is absent and `index` is first, so deep links to any tab, passive expiry, and successful logout resolve to `/` with no tab entry reachable through Back.

## Email, OAuth, logout, and expiry share Privy as authority

Removing `onAuthenticated` from `AuthFlowCard` eliminates a second navigation authority. Email verification remains in the OTP flow on a false result or error; publication of a user changes the root guard and removes `/access`.

OAuth targets `/access`, which maps to `app/(auth)/access.tsx` because route groups are pathless, and `app.config.ts` supplies the expected `perpal` scheme. A warm callback remains on the retained auth branch until Privy resolves; a cold callback first shows neutral restoration. Success lands on `/home`, while cancellation or failure remains unauthenticated without exposing tabs.

Account logout does not navigate optimistically. A ready-null transition removes tabs and creates `index`; an unexpected rejection keeps the account tab mounted and displays its error. Privy 0.70.6 declares `logout()` as always resolving, so the rejection branch is defensive and the provider’s user transition remains the effective success signal. Passive expiry has the same route behavior once Privy publishes ready-plus-null; mounted screens must not substitute for token validation at API boundaries.
